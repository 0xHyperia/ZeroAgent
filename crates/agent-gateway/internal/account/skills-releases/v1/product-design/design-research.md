# Research a product experience

## Frame the problem

Read supplied references and existing product conventions first. Identify user tasks, constraints, existing functions to preserve and the decision the research should inform. Ask only for missing information that materially changes the result; continue independent research meanwhile.

## Gather useful evidence

Use owned files and source for private context. Public search is available only in an explicitly approved public-research phase. Never put private screenshots, uploaded content, history, project details or account information into a search query or external URL. If research tools are unavailable, use supplied references and clearly identify gaps.

Compare relevant task patterns, not just colors or isolated screenshots: discovery, setup, main action, feedback, recovery and returning to work. For each pattern distinguish what was observed from what is inferred. Prefer primary documentation for technical capabilities. Cite real accessible sources; never invent a reference.

## Leave an implementable brief

Document the user task, complete flow, information architecture, desktop and phone layout, primary and secondary actions and important states. Cover loading, empty, error, permissions, cancellation, keyboard and reduced motion. Identify shared components and host-specific capabilities. Explain material tradeoffs and propose a direction that fits this product. Use design-ideate if visual alternatives are needed; use design-implement only after the intended direction is clear.
