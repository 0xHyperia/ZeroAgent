## 一行公共执行修复及撤销条件

`runtime/terminal/shell.rs:78` 的 Unix 外部命令从 `kill -TERM -<pid>` 改为
`kill -TERM -- -<pid>`，与现有 `runtime/process.rs` 安全参数模式一致。

| 项目 | 说明 |
| --- | --- |
| 需求 | 只停止应用拥有的目标私有进程组，保留其他进程组 |
| 上游缺口 | 负 PID 前未加 `--`。Ubuntu 22.04 的 procps kill 会误解析；不存在组 `-999999` 的最小对照也能触发错误 SIGTERM，原全库被 143 中断 |
| 撤销条件 | 上游原生使用安全参数，或 terminal 改用具备同等私有组保证的公共 helper 并通过对应实跑后，删除本地行 |

这属于必要的 Unix 公共执行修复，不承担旧数据或历史协议兼容。
最终文件 SHA-256 为 `b24041f2b5aa9beb57e01232410d96bdcd13338aa9435711d9cc5263a0a8b271`；
该文件相对本轮修复前恰 1 增 / 1 删，Windows cfg 分支排除这处变化。
原 143 执行、私有 PID namespace 中的原始参数对照及修复后真实私有组验证均保留。

## 测试夹具修正，未改变生产凭据规则

Unix 生命周期测试此前没有在 Windows 编译：一处 `other` 仍按旧方式构造普通 State，
而测试启动方法已要求 `Arc<Self>`。仅将该测试构造改为 `Arc::new`，保留原断言。

随后五个 Python 生命周期夹具被正常 Native capability hash 校验拒绝，不能进入其健康/取消场景。
新增明确的 `cfg(test)` capabilityless 入口和参数，仅这五个函数中的九处 Python 调用使用。
真实 sidecar 测试入口仍严格核对原 receipt；没有移除 receipt 或全局绕过校验。
去掉 test cfg 后，原生产四参数签名和调用 token 一致，原 capability block 逐字一致，
`supports_native_mcp_credentials` 未变。可复核证明见 `capabilityless-fixture-release-equivalence.json`。
这次 test-only 文件更新发生在 Windows C2 EXE 已完成、输入已冻结之后；不应描述为 C2 构建期间变化或全文件未变。

broker 则是独立 TempRoot 的测试全部固定使用 `fixture-profile`，碰撞了按身份复用的全局
ConfigurationCoordinator。并发的配置修订会按正常安全规则撤销另一测试的 pending recovery。
两份纯测试文件改为每个 TestProfile 一次 UUID，并贯穿绑定、host 和 coordinator 调用。
生产 broker、回收规则、原断言和并发度均未修改；旧高并发失败与新高并发通过均有原始 ELF 和日志。

这些失败不能改称历史通过：原完整库 143 记录、后续 1315 通过 / 6 失败 / 9 ignored 记录，
以及旧 broker 单项通过但高并发失败的记录全部保留。

## Protoc 与 Linux CI

Ubuntu 22.04 apt 的 Protoc 3.12.4 对当前 proto3 optional 要求实验开关，首轮 build.rs 因此失败。
本轮没有增加 Rust/proto 兼容开关，使用与本机 Windows 一致的
[官方 Protobuf 3.19.4](https://github.com/protocolbuffers/protobuf/releases/tag/v3.19.4) Linux 二进制。
工具镜像中第一次 ZIP 权限设置不完整的失败亦保留，之后验证非 root 用户可执行。

仓库 `mise.toml` 已固定 Protoc 34.0，工作流原先却直接 apt 安装未固定版本。
本轮窄修 CI：Linux release 固定 Ubuntu 22.04，两个 Native job 使用既有 mise 固定 Protoc，
发布 job 显式调用既有 GLIBC 脚本检查实际 `zeroagent` 路径。
Protoc 34 的独立工具/schema smoke 通过，但本机完整 Native 执行仍是 3.19.4，不能宣称完整 CI/Rust34 已运行。
