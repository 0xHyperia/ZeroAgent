## Windows shell 语义与旧记录

`internal/backend/cron_manager.go:249` 的 cron bash 执行使用 `bashrun.Run`。
`internal/tools/bashrun/shell.go:24` 的 Windows 默认优先 PowerShell 7，随后是明确路径的 Git Bash、
Windows PowerShell 和 cmd；`shell.go:70` 明确避开可能指向 WSL 启动器的裸 `bash.exe`。
本机解析结果也确实是裸 bash 指向 `C:\Windows\System32\bash.exe`，不能据此认定生产 cron 使用了 WSL。

本次测试启动器包含 Windows PowerShell 系统目录，不设置 `K_BRAIN_SHELL`，保留产品默认选择。
原样编码命令探测结果为 PowerShell 7 571 ms、Windows PowerShell 535 ms、明确路径 Git Bash 87 ms，全部退出 0。
探测不是 cron 业务验收；上表实际 cron 全包用例才是相应执行证据。

旧对照目录 `.codex-artifacts/mcp-backend-comparison-1792924124242/` 保持原状：

- `baseline-original-shell-path` 的 Hook 警告数为 9、预期 1。其 PATH 缺少 Windows PowerShell 目录；
  `internal/backend/hooks.go:421` 在 Windows 显式启动 `powershell.exe`。
  加回该目录后的原基线 Hook 用例通过。这一项有明确的启动器原因。
- `baseline-with-system-powershell` 中 AI approval、canonical MCP、Goal 和 Hook 通过，两个 cron 用例失败。
  `current-with-system-powershell` 的已有日志同样记录两个 cron 失败；日志仅记录等待时仍为 `leased`，
  或后续任务因前次仍在执行被跳过。`cron_http_test.go:348` 的等待窗口为 3 秒。
  旧记录没有足够信息证明它们由 shell 缺失、资源竞争或某个产品缺陷单独造成。
  本轮验证了实际 shell 路径并在当前四补丁源码完成定向和完整包复验，均未复现这些失败；未修改 cron 核心。
- `current-with-system-powershell` 没有 `result.json`，在 Goal RUN 后缺少终态；旧 PID 80680 已不存在。
  它仍是**未收集完的旧执行**，不能计为通过，也不再描述为运行中。

更早 `.codex-artifacts/mcp-runtime-go-full-1792900981192/` 中的 backend 失败也保留为历史失败：
AI auto-edit 写入超时、两个 cron 等待失败、MCP 仍 connecting、Goal 未 settle、Hook 警告数不符。
当前复验通过用于证明当前固定来源，并不改写旧执行结果或虚构其因果。

## 本次 Windows 首轮全包的启动夹具修正

首轮完整 Windows 执行（12:47:58–12:48:59 UTC）保留为 code 1：485 通过、3 失败事件、4 跳过。
3 个事件为 AI approval 父用例及 `automatic-low`、`run-auto-review-low` 两个子项。

原因是本次启动器把 TMP 放在含 `1792932272469` 时间戳的证据目录内。
工具写入路径因此包含该片段，`internal/privacy/gateway.go:47` 的 PHONE 规则匹配其中 `17929322724`，
`internal/approval/reviewer.go:147–151` 按现有安全规则将脱敏内容交回人工确认。
原始日志恰为 “Sensitive data was redacted; manual approval required”，因此两个预期低风险自动批准的夹具失败。

随后复用相同 SHA 的测试 PE 和相同源码，使用新的自有 HOME，将 TMP 改为不含时间戳的中性随机目录。
完整包在原 10 分钟预算内通过，安全规则和全部原断言均未变。
这是测试启动路径误触隐私保护的可复现原因，不需要增加协议兼容或放宽产品审批。
测试退出后中性 TMP 中的一份托管进程日志复制进证据目录，原临时目录已删除。
